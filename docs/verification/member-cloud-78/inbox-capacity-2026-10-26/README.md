## 发现及修复

首次队列在 `cec4bff` 上类型检查和客户端完整文件 14 项通过，原生专项为
13 项通过、1 项失败。Cloud 的 64 个产品输入在 1.27 秒内登记，但约 60 秒
仅完成 57 个原生投递，7 个尚未尝试，随后触发原有模型请求超时。
测试没有走到后续 Stop，不能把这个失败说成 Stop 本身失败。

成员内部投递只需要原生 Submission 回执，原实现却还读取整个会话来计算私聊展示
用的 disposition。队列增长时，这次额外的完整读取增加投递开销。
新增仅供有效成员租约使用的 `native-ack` 模式，返回 `submitted`，表示原生已入队，
不表示模型已读。返回前仍核对当前身份及原始提交；恢复检查、ACL、取消栅栏和
原生提交路径保留。私聊三参数调用继续返回 `started / queued / steered`。

修复后，同一 Cloud 容量用例在首次模型调用开始后 **40,017 ms** 内确认全部
64 个原生回执；63 条纠正消息登记耗时 944 ms。期间只有一次模型调用，
超限请求两次返回 409、原幂等回执可重放，读操作可用，Stop 结束原运行且保留
全部输入身份。没有增加 60 秒超时、容量、预算或重试次数。
